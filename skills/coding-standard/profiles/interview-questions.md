# Profile：面试深挖（interview-questions）

仅在面试深挖 Profile 开启时由 `SKILL.md` 加载并执行。默认关闭。

代码生成/修改完成后、自检通过并交付后，必须基于本次改动生成一份「面试深挖」面经。面经内容涵盖本次代码所涉及技术栈在中大厂面试中可能被问到的高频问题及标准答案，帮助开发者将日常开发沉淀为面试竞争力。

## 开启条件

1. 项目根目录存在 `.coding-standard.yaml` 且 `interview-questions: true`
2. 或用户口头要求开启（如「按 coding-standard 开启面试深挖」「生成面经」「面试深挖」）
3. 满足任一条件 → Read 加载本文件并执行
4. 否则 → **不加载**，不生成面经

```yaml
# 项目根目录 .coding-standard.yaml
interview-questions: true
```

## 面经生成时机

- 在代码自检全部通过、向用户交付最终代码之后
- 生成面经作为交付的一部分紧随其后
- 若本次改动极小（如单行注释修正、变量重命名），可声明跳过并说明原因

## 出题范围判定（★ 面经生成前必须先执行）

面经生成前，必须先根据本次改动的文件类型和影响范围，判定出题领域。**严禁在纯后端改动中出前端题，或反过来**，除非涉及跨端协议/接口变更。

### 判定流程

1. **识别改动文件的语言/框架类型**：
   - 检查本次改动涉及的文件后缀、目录结构、依赖声明
   - Java 文件（`.java`）、Spring 配置（`.xml` / `.yaml` 中 Spring 相关）、MyBatis Mapper（`.xml` 中的 SQL 映射）→ 归入「后端」
   - TypeScript / Vue / React 文件（`.ts` / `.vue` / `.tsx` / `.jsx`）、样式文件（`.css` / `.scss` / `.less`）、前端配置（`vite.config.ts` / `tsconfig.json` 等）→ 归入「前端」
   - 数据库 DDL / DML（`.sql`）、通用工具类、公共模块 → 根据实际使用方归入对应领域

2. **按领域锁定出题范围**：

| 改动领域 | 出题范围 | 例外说明 |
|----------|----------|----------|
| **纯后端**（仅有 Java/Spring/MyBatis 等后端文件变更） | 仅出后端方向题（Java、Spring、MyBatis、数据库、并发、网络协议） | 若本次改动涉及 API 接口签名/响应格式/错误码/鉴权方式变更，这些对前端有直接影响 → 可附加 1 道与接口契约相关的前端题（如「后端接口改动后前端如何适配」），但**不深入前端框架内部** |
| **纯前端**（仅有 TS/Vue/React/样式等前端文件变更） | 仅出前端方向题（Vue/React、TS 类型、CSS、浏览器、性能优化） | 若本次改动涉及调用后端接口的方式变更（如新增接口、调整请求参数/响应处理）→ 可附加 1 道与前后端协作相关的题（如「前后端联调时的鉴权方案」），但**不深入后端框架内部** |
| **前后端混合**（同时有后端和前端文件变更，或跨模块 API 协作变更） | 全量出题，后端与前端按改动占比分配 | 各板块的题目数量按改动占比大致分配，确保两边都有覆盖 |

3. **判定结果声明**：生成面经时，必须在面经开头声明判定结果，形如：

```
> 📌 出题范围判定：本次为【纯后端 / 纯前端 / 前后端混合】改动，出题聚焦于【后端 / 前端 / 全栈】领域。
> （可选）例外说明：因涉及 API 接口变更，附加 1 道前端协作题。
```

### 强制规则

- **禁止跨域出题**：纯后端改动中禁止出现 Vue 响应式原理、React hooks 原理、前端工程化等前端内部问题；纯前端改动中禁止出现 Spring IoC 原理、MyBatis 缓存、Java 并发等后端内部问题
- **共享基础可出**：以下主题属于跨端通用知识，后端或前端改动中均可合理出题：
  - 数据库与 SQL（MySQL 索引、事务隔离级别、SQL 优化）
  - HTTP/HTTPS 协议、RESTful 设计、WebSocket
  - 通用设计模式（单例、工厂、策略、观察者等）
  - 认证鉴权（JWT、OAuth2、Session/Cookie）
  - 缓存策略（Redis 缓存穿透/击穿/雪崩，浏览器缓存与后端缓存的区别）
  - 性能优化通用思路

## 面经结构

生成的面试题按以下顺序组织，每个部分必须包含「问题」和「参考答案」：

### 一、技术基础高频题（对应一面/笔试）

从本次代码涉及的技术点出发，挖掘大厂一面或笔试中的高频基础问题。

**出题来源参考**：华为、腾讯、阿里、快手、京东、字节、美团等中大厂真实面经

**出题方向**：

#### Java 后端方向（仅后端变更时出）

| 本次涉及的技术点 | 可能被问的方向 |
|-----------------|---------------|
| Java 语言特性（Lambda/Stream/Optional/泛型/注解等） | 原理、使用场景、坑点、源码级理解 |
| Spring 全家桶（Boot/Cloud/MVC/Security/Data） | 自动配置、AOP/IoC、事务传播、过滤器与拦截器区别 |
| MyBatis / JPA 等持久层 | SQL 注入防护、缓存机制、懒加载、N+1 问题 |
| 并发与线程安全 | synchronized/Lock、线程池、volatile、CAS |
| 网络与协议（RPC/gRPC/Dubbo等） | 协议选型、序列化方式、服务发现 |

#### TypeScript / Vue 前端方向（仅前端变更时出）

| 本次涉及的技术点 | 可能被问的方向 |
|-----------------|---------------|
| Vue 框架 | 响应式原理、虚拟 DOM、diff 算法、生命周期、Composition API |
| TypeScript 类型系统 | 泛型约束、条件类型、类型体操、类型推导边界 |
| 前端工程化 | Vite/Webpack 配置、Tree Shaking、Code Splitting |
| 浏览器基础 | 事件循环、渲染流程、跨域方案、存储方案对比 |
| CSS / 样式方案 | BFC、Flex/Grid 布局、CSS Modules / Scoped 原理 |

#### 跨端共享方向（后端/前端变更均可合理出）

| 本次涉及的技术点 | 可能被问的方向 |
|-----------------|---------------|
| 数据库（MySQL/Redis/ES等） | 索引优化、事务隔离级别、缓存穿透/击穿/雪崩 |
| 网络与协议（HTTP/HTTPS/WebSocket等） | 握手过程、安全机制、协议选型、RESTful 设计 |
| 认证鉴权（JWT/OAuth2/Session等） | 原理、安全性、前后端如何协作 |
| 设计模式 | 在代码中的具体应用、优缺点、替代方案 |

### 二、深度原理与源码题（对应二面/三面）

基于本次代码中用到的框架/中间件/设计模式，追问底层原理和实现细节。**出题领域严格遵循出题范围判定**。

**出题要点**：
- 追问「为什么这么设计」「源码怎么实现的」
- 追问底层数据结构、算法思想
- 追问异常边界和极端场景下的行为

### 三、系统设计与架构题（对应三面/交叉面）

从本次改动的功能域出发，延伸出相关系统设计问题。**纯前端改动时此板块可简化（仅当前端涉及架构级变更如状态管理方案、微前端等时出题）**。

**出题要点**：
- 如何从零设计一个类似的系统/模块
- 高并发、高可用、数据一致性方面的考量
- 技术选型的权衡与对比

### 四、场景题（重点★）

模拟面试官给出一个与本次代码相关的实际业务场景，考察候选人的分析思路和解决方案。

**场景题格式**：
1. **场景描述**：面试官口述的场景（含隐含的矛盾或坑）
2. **考点分析**：点出面试官真正想考察的能力点
3. **参考答案**：分步骤的回答思路

**场景题命题技巧**：
- 场景必须合理，不能凭空编造
- 通常包含一个「两难」或「坑」——比如改动会影响现有功能、性能与代码整洁的矛盾
- 参考答案要有层次：先复述理解 → 再拆解分析 → 最后给出方案和理由
- **场景题必须与改动领域一致**：后端改动 → 后端场景（如接口性能优化、数据一致性）；前端改动 → 前端场景（如组件重渲染优化、状态管理方案）

## 出题数量建议

| 本次改动规模 | 建议出题量 | 前后端混合时的分配建议 |
|-------------|-----------|----------------------|
| 小幅改动（单文件、单方法级） | 3-5 题，覆盖 1-2 个板块 | 按改动类型出一端题即可 |
| 中等改动（多文件、一个功能模块） | 6-10 题，覆盖 3-4 个板块 | 后端:前端 ≈ 6:4 或按实际文件变更比例 |
| 大幅改动（多模块、架构级变更） | 10-15 题，全覆盖 | 后端:前端 ≈ 5:5，或按实际模块比例 |

## 出题原则

1. **先判定领域**：生成面经前必须先执行出题范围判定，并在面经开头声明结果
2. **紧扣本次代码**：每一道题都必须能从本次改动的代码中找到落点——为什么这道题会被触发
3. **严禁跨域出题**：纯后端改动不出前端框架内部题，纯前端改动不出后端框架内部题；API 接口变更时可附加 1 道协作题作为例外
4. **真实可考**：题目应来自真实面试经验，不要编造偏门/冷门的理论题
5. **答案有深度**：参考答案不能只是概念定义，要有代码示例、实战经验、对比分析
6. **场景题是核心**：每个面经至少包含 1 道场景题，且场景要与改动领域和业务紧密相关
7. **简要申明**：生成面经前简短声明「正在生成面试深挖面经...」
