# 通用编码质量标准（语言无关）

目标风格：像有约 3 年全栈经验、吃透当前项目架构的中级工程师（R2）。

## 使用前提

1. **先读项目现有写法**：同层同类文件的命名、分层、注解、错误处理，优先对齐现有风格（R1）
2. **不绑定单一仓库**：规范通用；示例以 center（Java）与 Vue3+TS 为参考，落到具体项目时替换为该项目的包名/路径

## 禁止模式

| 禁止 | 说明 |
|------|------|
| 冗余封装 | 一层只转发、无业务含义的 wrapper / 过度抽象 |
| 兜圈子实现 | 能 `Stream.filter` / `list.filter` 就不要多层 `for-if-continue` |
| 「AI 味」代码 | 生硬命名、不自然缩写、无意义中间变量、注释复述代码 |
| 复制粘贴膨胀 | 重复逻辑应抽私有方法或工具，而不是整段拷贝 |
| 过早优化 | 无证据的缓存、异步、复杂设计模式 |

## 要求模式

- 直截了当：每一步对应明确业务含义
- 方法单一职责；单方法建议不超过 **50 行**（组装复杂 DTO / 构建复杂 SQL 可例外，但需分段清晰）
- 私有方法按功能分组，用分隔注释：

```text
// ======================== 查询辅助方法 ========================
```

- 变量名自解释；能靠命名说清的，不写废话注释
- 优先复用项目已有工具类、基类、统一响应与异常体系

## 代码常见问题速查

### 结构级问题

| 问题 | 信号 | 修复方向 |
|------|------|----------|
| 职责过多的类 | 单个类超过 300 行，承担 5+ 种职责 | 按职责拆分为多个小类，提取协作关系 |
| 长方法 | 单方法超过 50 行（组装 DTO/SQL 除外） | 按业务步骤切分，每个子方法只做一件事 |
| 长参数列表 | 方法参数超过 4 个 | 封装为 DTO/Options 对象；或检查是否职责太多 |
| 一处改动波及多处 | 改一个业务规则需要改 4+ 个文件 | 把散落的规则收敛到一个模块/方法中 |
| 一个类承担多种职责 | 同一个类因业务不相关的需求被频繁修改（比如今天改报表逻辑、明天改审批逻辑） | 按变化原因拆分类，每种职责一个类 |
| 深层嵌套 | if/for/try 嵌套 3 层以上 | 用 guard clause 提前返回；抽子方法降层 |
| 重复出现的字段组合 | 同一组字段（如 `x, y, width, height`）在多处重复出现 | 封装为值对象或独立 DTO |

### 命名与表达问题

| 问题 | 信号 | 修复方向 |
|------|------|----------|
| 含糊命名 | `data` / `info` / `temp` / `result` / `flag` | 用业务含义命名：`projectList` / `validationErrors` |
| 缩写泛滥 | `usrCfgBtnEvt` 等非通用缩写 | 用完整单词，除非已是行业通用缩写（`id`、`url`、`api`） |
| 注释复述代码 | `// 计数器加一` 上面是 `count++` | 删除注释；代码已经说明白了 |
| 魔法数字 | 代码里出现 `3`、`100`、`"admin"` 等无上下文字面量 | 提取为命名常量/枚举：`MAX_RETRY_COUNT`、`Role.ADMIN` |
| 布尔参数 | `doThing(true, false)` 调用方无法理解含义 | 拆成两个方法，或用 options 对象 |
| 基本类型用到底 | 用 `String` 表示电话号码/邮箱，到处重复校验 | 封装为值对象：`PhoneNumber` / `EmailAddress` |

### 快速自查清单

- [ ] 是否有只调用一次且无复用价值的私有方法被过度拆分？
- [ ] 是否存在可合并的连续判空 / 连续转换？
- [ ] 是否用了项目里已有的工具却又手写了一套？
- [ ] 控制流是否能用早期返回（guard clause）变平？
- [ ] 单个类/方法是否承担了过多职责？
- [ ] 同一个业务规则是否散落在多个文件中？
- [ ] 代码中是否出现了无上下文解释的裸字面量？
